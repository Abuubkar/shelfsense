# CI/CD: GitHub Actions checks on every PR, signed images from main

**Chosen.** `.github/workflows/ci.yml` runs on every pull request and every push to main. `release.yml` builds,
scans and signs images on main and `v*` tags. A slice merges once its PR is green (HOW_WE_BUILD §7).

- **Jobs** (ci.yml), each with read-only contents unless it needs more:
  - **lint:** ruff, mypy, tsc, eslint, and actionlint from its release tarball, checked against its published
    sha256.
  - **contracts:**
    - `make codegen` leaves no diff: clients, GraphQL schema, message schemas, index snapshots.
    - `make contract-check`: the code serves the spec.
    - Breaking changes against the base branch: oasdiff, graphql-inspector, and `check_message_compat.py`. A
      breaking change needs the `breaking-change-approved` label. A message changed incompatibly without a
      `schema_version` bump fails even with it.
  - **unit**, and **integration** on testcontainers (Postgres, OpenSearch, Floci), with `vm.max_map_count`
    raised and fastembed's models cached.
  - **migrations:** up, down to base, up again on Postgres. squawk lints the SQL of migrations the branch adds
    (`scripts/render_migrations.py --since`). Applied migrations can't change, so linting them is noise.
    `.squawk.toml` keeps the rules that enforce docs/migrations.md.
  - **index mapping:** a unit test against `contracts/index/<version>.json`. A version changed in place fails;
    fields added in place must be recorded.
  - **web:** jest.
  - **eval-offline:** the dev-split evals replayed from the committed recordings, with the search ablation run
    for real. It fails only on a regression against the base branch: a gated metric worse by more than 1.5
    points, or a gate the base passes that now misses. Known misses are listed in a sticky PR comment, not
    failed on. The gates themselves are unchanged, and `make eval` locally still exits 1 on any miss.
  - **perf-smoke:** only when search or API code changes. 5,000 seeded products, the API started without
    Ollama, then 500 searches with k6 drawn 60/30/10 from the golden head, torso and tail queries. It fails
    when the fast path's p95 is over 150 ms. Every parse path's latency is in the job summary.
- **Pinned:** every action by full commit SHA with the version in a comment; tools by exact version (uv 0.11.7,
  k6 2.3.0, squawk 2.71.0, oasdiff 1.35.0, graphql-inspector 7.0.2); the trivy image by digest.
- **Images** (release.yml): `ghcr.io/<owner>/shelfsense-{api,worker-enrich,worker-index,supplier-mock,web}`.
  - Build: linux/amd64 and arm64, with the GitHub Actions build cache.
  - Tags: `sha-…`, the branch, and semver on tags.
  - Supply chain: an SBOM and max-mode provenance attestation. trivy fails on a fixable CRITICAL
    vulnerability, and only images that pass are signed (cosign keyless, the workflow's OIDC identity).
  - Builds: one root Dockerfile with a target per Python service (uv, `--frozen`, non-editable, non-root uid
    10001, migrations shipped but never applied on start). The web app is a Next standalone server.
  - Review artifacts: a job renders every migration as SQL, plus the index-template diff since the previous
    push. Nothing applies them.
- **No live evals in CI:** runners have no GPU and no Ollama. Recordings, `REPORT.md` and results are committed
  from local runs.

## Alternatives

- **locust, or a pytest timing test, for perf-smoke:**
  - locust adds a Python dependency, has no built-in thresholds, and rounds latencies coarsely around 150 ms.
  - A pytest test needs no new tool, but we'd write the load, percentile and reporting parts ourselves.
  - k6 gives exact percentiles per tag and fails the run on a threshold, from a pinned binary.
- **eval-offline failing on every gate miss:** it would be red on every PR while main misses 7 gates, which
  teaches people to ignore it. Failing on regressions catches what a PR breaks, without moving a gate.
- **Linting every migration with squawk:** 77 findings in migrations already applied everywhere.
- **Baking fastembed's models into the images:** ready at start, but ~1.2 GB more per image, pushed twice per
  architecture on every merge. They download on first use into `/app/models`, a volume (docs/backlog.md).
- **paths-filter action for perf-smoke:** a `git diff` step does the same with one less third-party action.

## Assumptions

- Replays are deterministic across machines. The first CI run showed they weren't: on the x86 runner the
  embedding pre-filter put a different candidate in a prompt, and the replay missed. The live run's candidates are
  now recorded and replayed too (ADR 0018). The search section still embeds and reranks for real, so its numbers
  can move slightly between machines; the 1.5-point regression tolerance absorbs that.
- perf-smoke will miss its gate until reranking is fast enough on a CPU (`make eval-latency`: rules-path p95
  2,110 ms on an M1 Pro). The slice 7 PR stays open until the latency fix lands on the same branch.
