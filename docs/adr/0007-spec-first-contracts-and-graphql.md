# Spec-first REST contract, generated Python client, GraphQL beside REST

**Chosen.**

- **`contracts/openapi.yaml` (OpenAPI 3.1) is written by hand and is the source of truth.** FastAPI's emitted
  spec is compared with it by `make contract-check`, which runs oasdiff (`tufin/oasdiff:v1.35.0` in Docker) and
  fails on breaking changes. Nullable fields are written as `anyOf: [..., {type: 'null'}]`, the form Pydantic
  emits. oasdiff reads `type: [string, 'null']` against that as a widened type, a false break.
- **`packages/clients/python`** is generated by openapi-python-client 0.29.1 (`make codegen`), a uv workspace
  member, never edited by hand. Its first user is `scripts/smoke.py`.
- **GraphQL (Strawberry 0.339) at `/graphql`** for the UI's reads: `product`, `products` and `search` as Relay
  connections. Resolvers call `service.py`, as REST routes do. Each edge carries its own signed cursor. The
  schema is printed to `contracts/schema.graphql`, and a unit test fails if it drifts from the code.
- **Errors** are RFC 9457 `application/problem+json` with a `code` enum (docs/problems.md).

## Alternatives

- Code-first (FastAPI's spec as the truth): no review point for API changes before they're built.
- REST only: the plan wants GraphQL for the UI, for the hands-on experience (HOW_WE_BUILD.md §3).

## Assumptions

- Clients in other languages generate from the same spec; the TypeScript client arrives with the UI (slice 5).
